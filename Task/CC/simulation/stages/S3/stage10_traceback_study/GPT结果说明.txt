# 一、Stage10 的任务目标到底是什么？

Stage10 研究的不是“卷积码本身能不能纠错”，这个问题在前面的整块 Viterbi 阶段已经验证过了。

Stage10 真正要研究的是：

> **在不保存整帧全部幸存路径的情况下，Viterbi 只保留有限回溯深度 (D_{\mathrm{tb}})，会损失多少纠错性能，又能节省多少内存和输出等待？**

---

## 1.1 什么是回溯深度？

Viterbi 译码不是看到一个接收符号就立刻确定当前信息 bit，而是需要沿着网格图保留很多候选路径。

假设现在已经接收了 100 个输入时刻，但想判断第 30 个 bit，译码器会从当前最优状态沿幸存路径向前回溯：

```text
当前时刻
← 回溯 1 步
← 回溯 2 步
← …
← 回溯 Dtb 步
→ 决定一个较早的信息 bit
```

这里的 (D_{\mathrm{tb}}) 就是回溯深度。

例如：

* `Dtb=35`：只利用后续约 35 个 trellis 时刻来稳定决策；
* `Dtb=84`：等待更多未来信息再决定；
* `Dtb=306`：相当于保存整个 300 bit payload 加 6 个尾 bit，最后按完整块回溯。

---

## 1.2 回溯深度为什么需要研究？

因为它同时影响三类东西：

### 性能

回溯太浅时，候选路径还没有充分合并，译码器可能过早决定错误路径：

[
D_{\mathrm{tb}}\downarrow
\quad\Rightarrow\quad
BER、FER可能上升
]

### 存储

每个 trellis 时刻要保存 64 个状态的幸存路径信息，因此：

[
M_{\mathrm{survivor}}
\propto
D_{\mathrm{tb}}\times64
]

回溯越深，内存越大。

### 实时性

回溯越深，理论上一个 bit 要等待更多未来观测才能输出：

[
\text{首次稳定输出等待}
\approx D_{\mathrm{tb}}
]

所以 Stage10 本质是在寻找：

> **性能已经接近完整块译码，但内存和等待又明显更小的最小回溯深度。**

---

# 二、Stage10 当前具体做了什么？

本轮实验比较了：

```text
Dtb = 35、49、70、84、98、112
```

并加入：

```text
Dtb = 306
```

作为完整块零尾译码参考。

已有旧数据只覆盖 35、49、70 和完整块，本轮补跑了 84、98、112。审计报告将旧数据判定为 `DATA_PARTIAL`，而不是伪造或无效。

## 3.1 已经达到的目标

### ① 不同 Dtb 确实独立运行

不是把同一结果复制成几条曲线。

从 CSV 可以看到，随着 Dtb 改变：

* bit error 数改变；

因此参数研究是真实的。

### ② 已清楚找到性能饱和区

总体规律非常明确：

```text
Dtb=35：明显不够
Dtb=49：仍有较明显损失
Dtb=70：R12基本够，R23仍稍差
Dtb=84：所有当前场景进入设定的5%性能门限

```

Dtb=84 相比完整块的幸存路径内存降低：

[
1-\frac{16128}{58752}
\approx72.55%

这就是推荐表中的：

```text
survivorMemoryReduction = 0.72549
```

### ④ 已形成数据驱动的推荐

推荐结果为：

```text
performance-first：Dtb=112
balanced：Dtb=84
resource-first：Dtb=84
```

原因是 Dtb=84 是当前第一个在四个场景中都满足设定性能 Gate 的深度。

### ⑤ 绘图审计通过

四张图的：

---

## 3.2 尚未完全达到的目标

Stage10 可以判为：

```text
参数趋势研究：通过
当前候选中的阶段性推荐：通过
可直接作为最终工程参数：暂时不足
```

主要还有以下问题。

### 问题一：只有 1000 帧，低 FER 场景统计不够稳

例如 R12、0 dB、完整块只有：

```text
16 个误帧 / 1000 帧
FER = 0.016
```

Dtb=70、84、98、112 也都是 16 个误帧。

这说明它们在当前 1000 帧上相同，但不能证明真实 FER 完全相等。

因为 16 个误帧的统计波动不小。

后续应增加：

* 95% 置信区间；
* 或增加帧数；
* 或采用 `targetFrameErrors=200` 的停止条件。

---

### 问题二：只研究了 R12 和 R23，没有 R34

老师要求三个码率：

```text
1/2、2/3、3/4
```

当前 Stage10 没有正式研究 R34 的 Dtb。

R34 打孔更严重，可能需要比 R12 更深的回溯，不能直接把 Dtb=84 无条件推广到 R34。

至少应补：

```text
R34 soft
2～3个代表性SNR
Dtb=70、84、98、112
```

---

### 问题三：每种码率只取了两个 SNR

目前只在四个固定点研究。

这能看趋势，但不能证明：

> Dtb=84 在整个 waterfall 区都合适。

更理想的是每个码率至少覆盖：

```text
FER约0.3
FER约0.1
FER约0.03
```

R12 当前主要覆盖了约 0.059 和 0.016；R23 覆盖了约 0.231 和 0.088，并没有每种码率都覆盖三个层级。

---

### 问题四：时延图中的 Dtb=306 不能直接与有限回溯连线比较

这是四张图中最需要警惕的问题。

Dtb 35～112 使用的是：

```text
有限回溯译码实现
```

而 Dtb=306 使用的是：

```text
原有完整块 SoftViterbiDecoder
```

它们不是同一个程序仅改变一个 Dtb 参数。

所以图中出现：

```text
Dtb从112增加到306，
平均CPU译码时间反而明显下降
```

不是因为：

> 回溯越深反而越快。

而是因为：

> 完整块参考译码器的实现方式更高效，有限回溯版本每输出一个 bit 都重复回溯，操作数反而很多。

因此 Dtb=306 应画成：

* 单独的“完整块参考点”；
* 或水平虚线；
* 不应和有限 Dtb 用连续折线相连。

---

### 问题五：当前 CPU 时间不等于输出等待时延

Stage10 图里的“译码时延”是：

```text
CPU执行译码函数所消耗的微秒数
```

它不是：

```text
一个bit需要等待多少未来符号才能输出
```

真正的首次输出等待大致与 Dtb 有关，例如 Dtb=84 至少要等约 84 个 trellis 输入时刻。

因此后续应区分：

```text
计算时延：μs
决策等待：symbol / trellis step
```

当前图只回答了前者。

# 四、第一张图：回溯深度与误比特率 BER

## 4.1 纵轴 BER 是什么？

[
BER=
\frac{\text{译错的payload bit总数}}
{\text{总payload bit数}}
]

每个配置运行 1000 帧，每帧 300 bit，所以：

[
\text{总信息bit}=300000
]

例如 R12、-0.5 dB、Dtb=35：

```text
错误bit = 607
```

因此：

[
BER=\frac{607}{300000}
\approx2.023\times10^{-3}
]

---

## 4.2 四条曲线分别是什么？

图例：

```text
CC-B-R12-S--0.5
```

表示：

* `CC`：卷积码；
* `B`：整块场景；
* `R12`：码率 1/2；
* `S`：软判决；
* `-0.5`：SNR = -0.5 dB。

其余依次类推。

---

## 4.3 蓝线：R12、-0.5 dB

关键数据：

|    Dtb |      BER |
| -----: | -------: |
|     35 | 0.002023 |
|     49 | 0.001560 |
|     70 | 0.001507 |
|     84 | 0.001500 |
|     98 | 0.001500 |
|    112 | 0.001500 |
| 完整块306 | 0.001500 |

解释：

* Dtb=35 明显偏浅；
* 49 有明显改善；

* 84 之后继续增加深度，在这 1000 帧中没有再获得 BER 收益。

这就是典型的“先快速改善，后进入平台区”。

# 五、第二张图：回溯深度与误帧率 FER

## 5.1 FER 是什么？

只要一帧 300 bit 中存在至少一个错误：

```text
这一帧就记为误帧
```

[
FER=
\frac{\text{错误帧数}}{\text{总帧数}}
]

例如 R23、0.5 dB、Dtb=35：

```text
532帧错误 / 1000帧
FER=0.532
```

---

## 5.2 为什么 FER 通常比 BER 大很多？

假设某一帧中只错了 2 bit：

* BER 只增加 (2/300)；
* FER 直接把整帧记为错误。

所以图中可能出现：

```text
BER约10^-3
FER却约10^-2或10^-1
```

这很正常。

---

## 5.3 蓝线：R12、-0.5 dB

| Dtb |   FER |
| --: | ----: |
|  35 | 0.103 |
|  49 | 0.064 |
|  70 | 0.059 |
|  84 | 0.059 |
| 完整块 | 0.059 |

Dtb=35 时误帧率比完整块高：

[
\frac{0.103}{0.059}-1
\approx74.6%
]

而 Dtb=70 已达到相同 FER。

---

## 5.4 橙线：R12、0 dB

| Dtb |   FER |
| --: | ----: |
|  35 | 0.029 |
|  49 | 0.019 |
|  70 | 0.016 |
|  84 | 0.016 |
| 完整块 | 0.016 |

Dtb=35 的 FER 比完整块高约 81.25%。

说明即便 BER 的绝对差看起来不大，整帧成功率仍会明显恶化。

---

## 5.5 绿线：R23、0.5 dB

| Dtb |   FER |
| --: | ----: |
|  35 | 0.532 |
|  49 | 0.378 |
|  70 | 0.261 |

|  98 | 0.234 |
| 112 | 0.232 |
| 完整块 | 0.231 |

这是最能说明回溯深度重要性的一条曲线。

* Dtb=35：一半以上帧错误；
* Dtb=70：降到 26.1%；
* Dtb=84：24.1%；
* 完整块：23.1%。

Dtb=84 相对完整块的 FER 增幅为：

[
\frac{0.241}{0.231}-1
\approx4.33%
]

正好进入设定的 5% 门限。

---

## 5.6 红线：R23、1 dB

| Dtb |   FER |
| --: | ----: |
|  35 | 0.262 |
|  49 | 0.142 |
|  70 | 0.094 |
|  84 | 0.089 |
|  98 | 0.088 |
| 112 | 0.088 |
| 完整块 | 0.088 |

Dtb=70 相对完整块高：

[
\frac{0.094}{0.088}-1
\approx6.82%
]

Dtb=84 则只高约 1.14%。

---

## 5.7 第二张图的核心结论

FER 比 BER 对浅回溯更敏感。

尤其 R23：

```text
Dtb=70在BER上似乎已经很接近，
但FER仍可能高出6%～13%。
```

所以选择回溯深度时，不能只看 BER，必须重点看 FER。

# 六、第三张图：回溯深度与译码时延

## 6.1 这张图画的是什么？

纵轴表示：

```text
在当前电脑上执行一次译码函数的平均CPU时间
```

单位：

[
\mu s
]

它不包括真实通信传输时间，也不直接等于首次输出等待。

---

## 6.2 为什么 Dtb 从 35 到 112，时间总体增加？

有限回溯实现中，每接收一个新 trellis 时刻，就可能回溯 Dtb 步确定一个较早 bit。

回溯深度越大：

[
\text{每次回溯操作数越多}
]

例如总回溯操作数：

| Dtb | traceback operations / 1000帧 |
| --: | ---------------------------: |
|  35 |                    9,520,000 |
|  49 |                   12,642,000 |
|  70 |                   16,590,000 |
|  84 |                   18,732,000 |
|  98 |                   20,482,000 |
| 112 |                   21,840,000 |

所以 CPU 时间通常上升。

---

## 6.3 为什么曲线不是严格单调？

例如某些场景中：

* Dtb=98 比 112 稍慢；
* 或不同 SNR 曲线有轻微波动。

这通常来自：

* CPU 调度；
* 缓存状态；
* 后台程序；
* 计时噪声；
* 操作系统频率调整。

几微秒至十几微秒的小差别，不宜解释为算法规律。

---

## 6.4 为什么 Dtb=306 突然降到约 274～286 μs？

这是这张图最容易误读的地方。

Dtb=306 使用的是完整块参考译码器，而不是继续使用有限回溯函数。

完整块译码器：

* 完整前向 ACS；
* 最后统一回溯一次。

有限回溯译码器：

* 在运行过程中反复进行长度 Dtb 的回溯；
* 重复回溯的总操作数反而很大。

因此完整块的 CPU 时间更短是“实现策略不同”造成的，不代表：

> 回溯深度 306 比 112 更适合低时延实时输出。

完整块仍然必须等整帧到齐后才能输出，而有限回溯可以较早逐 bit 输出。

所以：

```text
CPU计算时间较短
≠
首次输出等待更短
```

---

## 6.5 这张图应怎样改得更合理？

建议把它拆成两部分：

### 图 A：有限回溯计算时间

只画：

```text
Dtb=35、49、70、84、98、112
```

### 图 B：完整块参考

用单独柱子或虚线标出：

```text
BLOCK_FULL_TRACEBACK
```

并注明：

```text
完整块与有限回溯为不同实现，CPU时延不可视为同一算法的连续趋势。
```

# 七、第四张图：回溯深度与幸存路径内存

## 7.1 为什么是直线？

每个 trellis 时刻需要为 64 个状态保存一个 `Survivor`。

当前 `Survivor` 占约 3 byte：

```text
predecessor
input
valid
```

所以：

[
M_{\mathrm{survivor}}
=====================

D_{\mathrm{tb}}
\times64
\times3
]

例如 Dtb=84：

[
84\times64\times3
=================

16128\text{ byte}
]

---

## 7.2 各 Dtb 内存

| Dtb |      内存 |    约合 KiB |
| --: | ------: | --------: |
|  35 |  6720 B |  6.56 KiB |
|  49 |  9408 B |  9.19 KiB |
|  70 | 13440 B | 13.13 KiB |
|  84 | 16128 B | 15.75 KiB |
|  98 | 18816 B | 18.38 KiB |
| 112 | 21504 B | 21.00 KiB |
| 306 | 58752 B | 57.38 KiB |

---

## 7.3 为什么四条线完全重合？

幸存路径内存只取决于：

```text
Dtb
状态数64
每个Survivor字节数
```

它与：

* SNR；
* 码率；
* 误码率；

无关。

所以四个 Case 的内存完全一样，曲线重合。

这张图实际上只需要一条线。

现在保留四条图例会让读者以为码率或 SNR 会影响内存，反而增加困惑。

---

## 7.4 Dtb=84 节省了多少？

相对完整块：

[
\frac{58752-16128}{58752}
\approx72.55%
]

也就是说：

> Dtb=84 只使用约 27.45% 的完整 survivor 内存，节省约 72.55%。

这就是 Dtb=84 的主要工程优势。

---

# 八、为什么最终推荐 Dtb=84？

当前 Gate 规则是：

```text
优选门限：
最坏BER相对增加 ≤ 5%
最坏FER相对增加 ≤ 5%
```

Dtb=70 的最坏情况来自 R23：

* BER 增加约 5.70%；
* FER 增加约 12.99%。

所以 Dtb=70 失败。

Dtb=84 的最坏情况是：

* BER 增加约 2.88%；
* FER 增加约 4.33%。

两者都不超过 5%。

同时它比完整块减少约 72.55% survivor 内存。

因此：

```text
Dtb=84
```

是当前候选中第一个同时满足：

* 性能 Gate；
* 显著节省内存；

的深度。

Dtb=98、112 性能更接近完整块，但内存更大，而性能提升已经非常小。

# 九、我对当前 Stage10 的最终判断

## 可以保留的结论

在当前条件下：

```text
300 bit
K=7
软判决Viterbi
R12和R23
四个代表SNR
每配置1000帧
```

可以合理得出：

> Dtb=35 明显不足；Dtb=49 仍存在较明显损失；Dtb=70 对 R12 基本足够，但对 R23 尚不稳定；Dtb=84 是当前性能与 survivor 内存之间的合理平衡候选；Dtb=98 和 112 更接近完整块，但边际收益很小。

---

## 不能过度延伸的结论

当前还不能说：

```text
Dtb=84是所有卷积码场景的最终最佳值
```

因为尚未充分覆盖：

* R34；
* 更多 SNR；
* 复杂信道；
* 真滑窗实现；
* 更大统计样本；
* 硬判决；
* 实际硬件周期和内存布局。

# 十、Stage10 后续应补哪些内容？
